# Changelog

## 2026-09-01

### Feature

- **`time_slots.capacity` is enforced.** It has been editable in the dashboard, returned by the API and applied nowhere since P4 — fifty customers could all pick «3–6 مساءً» and nothing said no. A field operations can set and the system ignores is worse than no field, because somebody sets it and believes it (Service / API).
- **A booking is a visit, not an order.** A pickup and a delivery in the same window are two journeys to two doors, so both consume a place; counting orders would let a day quietly carry twice the traffic it was configured for. A cancelled order gives its place back — one abandoned booking must not block a window all day (Service).
- Per window, per day, across the platform, because that is what the column can say: it carries no city and no laundry. Capacity that varies by either is a different column and a different conversation (Service).
- **The app can see it before it submits.** `GET /time-slots?date=` returns `remaining` and `is_full` per window, so a full one is greyed out rather than refused after the customer has filled in the whole wizard. `remaining: null` (uncapped) and `0` (full) are kept distinct — the app has to draw them differently (API).
- Claimed inside the order's own transaction with `lockForUpdate` on the slot row: two customers submitting into the last place at the same instant would otherwise both read "one left". The lock is on the window, so bookings into different windows never wait for each other (Service).
- Rescheduling goes through the same check — otherwise a full window is reachable by postponing and rebooking into it. **A confirmed repeat-schedule prompt is the one exemption**: the customer was asked «محتاج تغسل النهاردة؟» and said yes, and that screen has no slot picker to send them back to. Turning away the most loyal customer there is over a number they never saw is the platform's problem to absorb (Service).

- **The slot list shows the capacity being used.** Booked today and booked tomorrow, per window, with a full one marked — because a number operations can set and never watch is a number somebody sets once and forgets. Today is what is happening; tomorrow is what can still be re-staffed (Service / Blade).

- **`GET /catalog` takes `service_id` and `category_id`.** Unfiltered is still the whole grid, which is what «الاسعار» wants — the customer is comparing services and a call per service would be a call per tap. The filters are for the order wizard, which already knows the service (API).
- **`GET /cities` takes `city_id`.** The default still fills both of the address form's dropdowns in one call: they are filled together, and a round trip between picking a city and seeing its zones is a spinner in the middle of a form (API).
- Both refuse an id that does not exist with a **422** rather than falling back to everything. Widening a filter in silence is how a dry-cleaning price ends up on a wash-and-iron screen. An inactive city asked for by id comes back empty, so the filter cannot reach an area we stopped serving (API).

- **«تتبع المندوب مباشرة» — the moving dot.** Two designed screens depended on it and nothing existed on either side: no coordinates, no way to report them, no way to read them. Built to the owner's decision — the last point only, every thirty seconds, and only while a journey is in progress (Database / API / Service).
- **Three columns, not a table.** The design draws one moving dot and no trail; a points table would be the largest in the system inside a month — a driver reporting every thirty seconds over an eight-hour shift is about a thousand rows a day, each obsolete thirty seconds after it is written (Database).
- **A driver between jobs is not tracked.** The write is refused and the reply says `tracking: false` so the app stops asking. Following somebody who is not working is not a feature of a laundry (API).
- **The map is limited to the two legs that end at the customer's door.** Legs two and three run between the laundry and back and the customer is waiting at neither end — a live position for a journey nobody is waiting on is surveillance with no purpose (Service).
- **A reading older than two minutes is removed, not frozen.** Four missed reports is a phone that lost signal or ran out of battery; a marker left where it was reads as «السائق واقف» and sends the customer to the telephone (Service).
- The columns are **not fillable**, so no profile update can move a driver on the map, and the endpoint is throttled at fifteen times the app's own rate — enough to stop a looping build, never enough to silence a working driver (Model / Provider).

- **«ادعُ أصدقاءك» — the referral programme.** On the final account screen with nothing behind it. Built to the owner's decision: both sides get a coupon, **after the friend's first paid order**. That timing is the feature — a reward at sign-up is free to manufacture, and a programme that pays on registration is one somebody farms with five phone numbers (Database / Service / API / Blade).
- Paid from an `updated` hook on the order rather than from the two places that settle payment. Cash on the doorstep and a captured card both mark an order paid and a third way will arrive; hanging the reward off the transition means the new one cannot be the one that forgets. Stamped once per customer, so an order marked paid twice pays once (Model / Service).
- **`coupons.user_id` — a coupon only one named person can use.** Coupons here have always been public codes limited by a redemption count, and a personal reward issued as a public code is a reward for whoever hears about it first. A stranger trying one is told it does not exist rather than that it is not theirs (Database / Service).
- **The reward is off until somebody sets it.** Its size is a business decision, not a default worth inventing, so an unconfigured install records the referral and issues nothing — and filling the setting in later does not open a bill for every friend who has already ordered. Two fields on the settings screen, and `GET /referral-terms` so the register screen states the offer instead of hardcoding a figure that changes (Setting / API).
- `GET /referrals` reports **both halves** — who joined and who actually ordered. Somebody who shares a code and sees nothing happen shares it once, and the gap between the two numbers is the whole story of the programme (API).

- **A Figma sweep against the API — 168 designed frames against 96 endpoints.** Six of the holes it found are closed here. Each was a control the design has drawn since the first version with nothing behind it, and none of them failed loudly, which is how they survived nine phases (API / Service / Database / Blade).
- **«إظهار رمز الاستلام (QR)».** The button is on three customer screens and `qr_token` had never left the server — the driver was given it yesterday, the customer never. It is on the order detail now, behind the same ownership boundary as the rest of the order (API).
- **«مندوب الاستلام · أحمد · ★ 4.9».** The tracking endpoint returned **no driver at all**: a customer waiting at home could see that somebody was on the way and not who. It now names whoever holds the leg in flight, falling back to the last completed leg so an order sitting at the laundry still names the person who collected it (Service / API).
- The star is the average of **`order_ratings.delivery` alone**, which is why that column was kept separate from `service_quality` in the first place — averaging the aspects would mark a driver down for a badly ironed shirt. Null rather than zero until somebody has rated them: a new driver shown as 0.0 reads as a bad one. **No phone number** — handing a driver's personal mobile to every customer is a policy decision, not a field, and the design shows no call button (Service).
- **«المرفقات» on complaints.** The form has carried a photo attacher since the first design and the endpoint took text only — for the complaints this feature exists for, a stain that did not come out or a torn seam, the photograph is most of the evidence. Up to five, images only, and shown on the operations screen: an attachment nobody can see is worse than one that was never accepted, because the customer believes they have shown somebody the stain (Database / API / Blade).
- **«مستندات المركبة».** The columns have existed in `driver_profiles` since P5 and the payload never returned them, so the row in the driver's account opened on an empty page. Returned read-only with their expiry dates — a verified record a driver can edit is not a verified record (API).

- **«مرجع العميل» — the number printed on the bag.** The driver's ticket card (Figma `193:2391`) carries it beside the order number and the two are not interchangeable: the order number identifies one job, the reference identifies the person, permanently. It is what lets a laundry match a bag whose label is torn, and what lets a returned garment find its owner (Database / Model / API / Blade).
- Deliberately **not** the user id. Drivers, staff and admins share the `users` table, so the id sequence has gaps — telling the 3rd customer they are the 12th. It is sequential over customers alone, assigned by a `created` hook on the model rather than at each registration path, because there are four ways a customer row comes into being and a path that forgets produces a bag with nothing printed on it — discovered by a person holding the bag rather than by anything that fails (Model / Service).
- The next number is read off the **highest existing reference, not a row count**: a deleted customer must not hand their number to somebody else, because the reference is printed on labels that outlive the account. Existing customers were backfilled oldest-first (Migration).
- **The printed card's contents are assembled server-side** and served with the driver's task — order number, customer reference, service, date, destination and the QR. Piecing it together in the app from four other fields is how a label ends up on the wrong bag, which is found out when the clothes come back to the wrong person (API).
- The reference is **searchable** on the customers screen and shown on the customer's page. Somebody at the counter holding a parcel has the reference and nothing else (Repository / Blade).

- **«تنظيف جاف» can finally be priced.** A quote-mode service carries no catalogue prices by design — what a suit costs depends on the fabric and the stain — and the review screen rendered *nothing* for one. The order could be placed and then never priced, stranding it at `picked_up` with no way forward (Service / Request / Blade).
- The laundry now types the unit price beside the count, per line, which keeps the customer's comparison screen and the invoice itemised exactly as they are for every other service. Every active piece is offered, since there is no matrix to filter the catalogue by (Service / Blade).
- **A posted price can never re-cost a catalogued service.** The value is accepted, validated and then ignored for anything priced per item; only a quote-mode service reads it. A counted piece left without a price is refused rather than cleaned for free, and a piece counted down to zero needs no price at all (Service).
- A re-count keeps the prices already entered — a dispute is usually about the count, and making the laundry retype every price is how a second count becomes a third (Service).

- **Weekly report emails — `laundo:weekly-reports`.** The owner's decision: a summary to the super admins, and each laundry its own. The four reports have always been on the dashboard and have always exported; what was missing is that somebody has to remember to open them, and the laundry owner who never logs in is the one whose numbers are falling. Sunday 08:00, covering the seven days up to and including yesterday, so the email is never about a day still in progress (Console / Mail / Blade).
- **A laundry's figures come from the same report services run as that laundry's owner**, so the tenant scope does the filtering. A parallel set of `where laundry_id` queries inside a mailer is how the emailed number and the on-screen number drift apart with no way to tell which is wrong. The borrowed identity is put back in a `finally` — leaving an owner logged in would silently scope every command that ran afterwards (Service).
- The figures are in the **body**, not only the attachment — this arrives on a phone on a Sunday morning — with the CSV alongside, BOM-prefixed so Excel opens Arabic as Arabic. The queue of things waiting for a person sits above the statistics, and a zero never appears in it. One bad address is logged and skipped rather than thrown, because a scheduled command that dies halfway leaves no record of who did get one (Mail / Console).

- **A Postman collection for the API — `docs/postman/`.** All 95 routes under `/api/v1`, in 20 folders, with the environment beside it. The API has been built out over six phases and the only description of it was `routes/api.php` itself; anybody integrating against it was reading a controller to find out what a request body looks like (Documentation).
- **Auth is wired, not described.** The collection authenticates at the collection level, public routes carry an explicit *No Auth*, and the three driver folders override the token — so a customer token reaching a driver route stays the routing question it is in the code. Login, Verify OTP and Driver login write their token into a variable from a test script, and the requests that create an address, an order, a complaint or a schedule capture the new id, so a run through a folder works without copying ids by hand.
- Every request asserts the `key` + `code` envelope, since it is uniform across all 95.
- The defaults point at `DevFixturesSeeder`'s accounts rather than placeholders — a collection whose first request fails against a freshly seeded database teaches the reader nothing. Verified by driving 26 requests, both roles, straight out of the generated file against a running server; coverage is asserted against `route:list`, and the README carries the drift check to re-run after a route changes.

### Documentation

- **The Postman collection is level with the code again** — 98 requests against 98 live routes, verified by diffing the collection against `route:list` rather than by reading it. Added the three endpoints built today (`POST /driver/location`, `GET /referrals`, `GET /referral-terms`) and a `20 · Referrals` folder (Postman).
- Seven existing requests were describing an API that had moved underneath them: `register` now documents `referral_code`, both order endpoints document that `payment_method` accepts `instapay` and changes the total, `Show order` documents `qr` and `cash_surcharge`, `Track order` documents the whole driver card including the live dot and the four cases where it is deliberately null, `Submit a complaint` documents `photos[]`, and `Driver profile` documents `documents[]` (Postman).
- **An API reference page** covering every endpoint: what it is for, every parameter with type and whether it is required, and the non-obvious rules. Parameters are extracted from the FormRequests and the controllers' own `validate()` calls rather than written from memory, and the page is checked against the route table so it cannot describe an endpoint that does not exist or miss one that does (Documentation).
- The reference page is **in Arabic and right-to-left**, which is the language the people reviewing it work in. Technical identifiers — paths, parameter names, enum values — stay in Latin and are marked `dir="ltr"` so they do not reorder inside Arabic sentences (Documentation).
- The page closes with **eleven places the API looks wrong and is not** — POST-for-update, a POST that reads, a GET that builds a basket, a confirm that takes a payment method, a withdraw that moves no money, and the rest — each with the reason, in English and Arabic. Written because the reasons live in code comments today, which is the wrong place for somebody deciding whether the design is right (Documentation).

### Fix

- `TimeSlotController@index` pulled one key out of `shredData()` instead of passing the result through, which is the module convention everywhere else. Adding a second key to the service left it undefined in the view — caught by the test, but the cherry-picking was the bug (Controller).

- **An inserted method stole the docblock below it.** Adding the order's `booted()` hook immediately above `tasks()` left that relation's `@return HasMany<OrderTask, $this>` attached to the hook, and the relation silently degraded to `Model` — which surfaced two files away, in `RescheduleService`. The same mistake was already sitting in the `Driver` model, where `profile()`'s docblock had been orphaned onto `tasks()`; both are fixed (Models).

- **«انستا باي» was priced and then refused.** `OrderRequest` hand-listed `['cash','card','wallet']` while the enum, the quote endpoint and the payment endpoint all carry InstaPay. A customer could pick it on the payment screen, see the price, and have the order rejected at the last step. Read off the enum now, so the four places cannot disagree again (Request).
- **The cash surcharge had no line on the placed order.** Added to the quote yesterday and nowhere else, so a customer looking at the order they had placed saw a total carrying a fee they could not check. It is its own line in the order payload now, zero rather than absent for every other method (API).

- **A column allow-list hid `pricing_mode`, and every order claimed to be quote-priced.** `OrderRepository::EAGER` selected `service:id,name`, so `isPerItem()` read null and answered false — which does not fail, it silently inverts. Caught only because the new quote-pricing branch made the wrong answer visible; before today nothing read the flag off an eagerly-loaded service. The same trap in the same hour also hid `customer_reference` from the driver's ticket (Repository / Controller).
- **The customers screen's status toggle was disabled for everyone but the super admin.** `:permission="canDo('user.toggleStatus')"` passed a *boolean* into a component that calls `canDo()` on what it is given, so the check ran against the coerced string `"1"` — and `user.toggleStatus` is not a permission slug in the first place; the generator's action is `toggle`. Every other module passes the string correctly. Also fixed the empty-state `colspan`, which was one wider than the table (Blade).
- `superAdmin()` in the test harness inserted a new row on every call, so a test checking two screens in one block hit the `users.phone` unique index. Its identity is fixed, so it is `firstOrCreate` now (Tests).
- A payments test asserted that a payment two days old still counted toward the month. True on 28 days out of 30, and today is the 1st — the kind of test that fails on exactly the days somebody would doubt the screen. It travels to mid-month now (Tests).

## 2026-08-31

### Feature

- **`Cash_Surcharge` is finally charged.** «قد يتم تطبيق رسوم إضافية» — the field has been on the settings form, validated and stored since P9, and **nothing read it**. A surcharge configured by an owner changed no price at all: the most complete kind of silent failure, because the settings screen said it was working. A fixed amount, not a percentage — `max:1000` next to `Driver_Earning_Rate`'s `max:100` settles that (Service / Database / API).
- Applied **after the discount**, deliberately: a coupon discounts the washing, not the cost of handling notes. Discounting the surcharge would mean a large enough coupon paid the customer to use cash. Shown as its own line in the quote, since a charge a customer cannot see is a charge they cannot avoid — and this one they can, by paying another way (Service / API).
- Recorded on the order in a new `cash_surcharge` column. Without it `estimated_total` is a figure nobody can reconstruct, and an invoice printed after somebody edits the setting would disagree with the order it was printed from (Database).
- A quote taken **before** the customer has chosen how to pay shows no fee; a card or wallet order records zero rather than null, because every order has a surcharge and for almost all of them it is nothing — null would mean "unknown", which is not a state this can be in (Service).

- **A payments screen** at `/admin/payment`. Payments were visible inside a single order and nowhere else, so a day's takings could not be reconciled against the gateway without querying the database by hand (Controller / Blade).
- It leads with **what is stuck, not what worked**: authorisations never captured — money the customer believes they have paid, we have not taken, and the hold expires — and payments pending over an hour, which is a gateway round trip measured in seconds, so it is an abandoned redirect or a webhook that never came. Both sort to the top of the list; newest-first buries the only rows anybody needs to act on (Controller).

- **A driver earnings screen** at `/admin/earning`. Earnings existed solely in the driver's own app, so operations could not answer "what is this driver owed" — a question drivers ask and the platform is legally the one holding the answer to (Controller / Blade).
- It leads with **what is owed, not what has been paid**, and groups it per driver, most-owed first, because the question is who to pay rather than who exists. "Released" is labelled as *became withdrawable* and not *paid out*: paying a driver happens outside this system, and conflating the two would overstate what has left the bank (Controller / Blade).
- Neither screen is tenant-scoped and neither model uses `BelongsToLaundry`, on purpose: a payment is the platform collecting money and an earning is the platform owing it — a laundry is party to neither. `payment.view` and `driver_earning.view` are granted to the super admin alone, and that permission is the whole protection (Routes / Model).

- **All five of the owner's decisions are built.** Each had been sitting as an assumption I chose; they were answered and are now code (Service / API / Console / Helper / Blade).
- **A closed complaint tells the complainant.** One push at closure, quoting the `CMP-` reference. Resolved and closed are worded differently on purpose — "we sorted it out" and "we looked and decided not to act" are not the same message, and sending the first for the second invites a second complaint (Service).
- **`orders:alert-silent-confirmations`.** After 24 hours at `reviewed`, both sides are nudged and **nothing happens automatically** — auto-confirming a price nobody read is a dispute waiting to happen. Sent **once per order, ever**, with the notification log as the memory: an alert that repeats hourly teaches people to ignore it, and then the one that mattered is ignored too. Scheduled hourly, because "24 hours" checked once a day means up to 48 (Console).
- **A per-subject hourly notification cap.** An order moving three stages in a minute sent three pushes and nothing limited anything. Transactional events are exempt — the final-price notification stalls the order when missed, so it is never a candidate for silence — and the cap is scoped to the subject, because two orders moving at once are two conversations. Counted from the log's `database` rows, since every message writes exactly one (Service / Config).
- **Dashboard data columns follow the panel language.** A reversal of the first-phase convention, done in one helper so all 62 call sites follow. What makes it safe is a shared fallback chain — the panel language, then the default, then any value present — so a laundry whose Arabic name was never filled in shows in English rather than reading "No Data Found" and becoming unsearchable (Helper).
- `getLocalizedValue` (the API side) now shares that chain. It used to end in a hardcoded `?? ->ar`, which made Arabic the last resort even on an install whose default language is English (Helper).

- **Retention — `laundo:prune`.** Three tables had no bound at all: `notification_logs` (one row per channel per notification, including deliberate skips), `payments.payload` (the provider's JSON, verbatim) and `device_tokens` (removed only on a permanent Firebase rejection, so a handset nobody uses stays for ever). None was a problem today; all three become one at the volume this business intends to reach, and the moment to decide retention is before deleting from the table is itself an operation. Scheduled weekly, Sunday 03:30 (Console).
- The command follows three rules, each with a test: **nothing still needed is touched** — a failed log is kept four times as long as a delivered one, because a failure is what somebody investigates months later; a payment's **payload is cleared, never its row**, because the row is the money; and **`--dry-run` first**, so the first production run can be read before it is trusted. Deletes are chunked, because a single delete over a year of logs holds the table for as long as it takes (Console).
- **`GET /api/v1/translations/{app|web}`.** The languages screen has always let an admin upload a mobile or web translation file, and `getTranslationFile()` has always been able to read one — with no caller anywhere. The upload wrote a file nothing served: a column with no form field, from the other direction. The `panel` set is deliberately not served; no app has use for a thousand admin strings (API).

- **The dashboard home page was replaced.** It opened with total customers, total laundries, total categories and total banners — none of which changes during a working day, and none of which anybody could act on. "Total Banners: 0" is a row count, not a figure (Controller / Service / Blade).
- The page is now built on one rule: **every number is either something happening right now or something waiting for a person.** Anything that fails that test belongs on the reports screen (Service).
- **The queue comes first**, above every statistic, because it is why somebody opened the page: orders with no laundry, journeys with no driver, customers waiting to confirm a price, open complaints, refunds to decide, journeys that ran out of attempts, wallets that disagree with their ledger. Each row carries the count, **why it matters**, and a link — a number nobody can click is a number they have to go and find (Service / Blade).
- **A zero never appears in that queue.** A column of noughts trains people to stop reading the list, and then the one that is not a nought goes unnoticed. When nothing is waiting the page says so in words (Service).
- «Right now» shows **where every live order physically is** — booked, with a driver, at a laundry, ready to go out, delivered and unpaid. That is the question a person actually opens a dashboard with, and no count of rows answers it (Service).
- **The two roles get different pages, because they do different jobs.** A laundry owner sees its working day in the order it happens — waiting to be counted, priced and waiting for the customer, confirmed and not started, in cleaning, ready — with a note on each saying what is being held up. A platform operator sees dispatch, drivers, platform money and an oldest-problem-first attention list (Service / Blade).
- Driver figures are **withheld** from a laundry rather than filtered, and the reason is written where somebody will find it: tasks carry no `laundry_id`, so `BelongsToLaundry` offers no protection over them at all (Service / Controller).
- Definitions are taken from the existing report services wherever one exists — money today is dated by `paid_at`, the same rule `RevenueReport` uses — so the home page and the reports cannot disagree about the same day's revenue (Service).
- **`ComplaintReceived` notifications.** A new complaint now alerts the operators through P11's dispatcher, so the queue works without somebody remembering to open it. Transactional, because a muted operator is still the person who has to answer; non-throwing, because a Firebase outage must not lose an accepted complaint (Enum / Service).
- **An operator inbox** at `/admin/my-notifications`. The topbar bell is a ten-item dropdown, and an operations alert that scrolled past the tenth was simply gone — a poor fate for the only warning that a task has had no driver for six hours (Controller / Blade).

- **Task 3 of the gap audit — P10 support and complaints.** «المساعدة والدعم» is a section in the driver's account screen with three items, and a button on the customer's order-detail screen. «تواصل معنا» was already done yesterday — the contact details reach the apps through `/app-settings` — so what was missing was the FAQ and the complaints (Database / API / Service / Blade).
- **FAQ:** a content module with an `audience` column, because both apps show the same section and the answers are not the same — a driver asking when they get paid and a customer asking when they get their clothes must not read each other's list. `GET /api/v1/faqs?audience=customer|driver`; an unspecified audience returns everything rather than guessing, since guessing from an absent token is how one app quietly gets the other's answers (Module / API).
- **Complaints:** `POST`/`GET /api/v1/complaints`, a queue screen, and a `ComplaintCategory` closed set so «أكتر سبب شكوى إيه» has an answer — free text alone leaves that unanswerable unless somebody reads every row, which nobody does past a few hundred. `Other` is in the set deliberately: without it a customer with a real problem picks the nearest wrong category and the tally becomes a lie (Database / API / Blade).
- `order_id` is **optional**, because the two entry points are not the same shape: the driver complains about nothing in particular from their account screen, the customer complains about an order. A named order is checked against the complainant's own orders, so a stranger's order id is a refusal rather than a complaint filed against a laundry over an order they have never seen (Service).
- **Operations answers by phone, per the owner's decision, so there is no reply thread** — and the consequence needed handling: a complaint that lands and shows nothing back is a black hole. It returns a quotable `CMP-XXXXXXXX` reference and the complainant can see the status move. The `internal_note` is never in a customer-facing response; it is where operations writes what was said on the call, and notes **append rather than replace**, because two people working the same complaint over a week is how "we already told them that" gets lost (Service / API).
- **A low rating with a comment appears in the same queue.** The rating form's own placeholder is «اكتب ملاحظاتك أو شكواك», so those are complaints that arrived through another form. Kept as a separate table on the same screen rather than merged into the paginator — different table, different actions, and a "resolve" button there would have nothing to resolve (Controller / Blade).
- The queue sorts **oldest open first** and counts the ones waiting over a day. "Newest first" buries exactly the wrong complaint, and a total never says whether the queue is being worked (Controller).
- `complaint.*` is granted to the **super admin only**, which is the whole protection: `Complaint` carries a `laundry_id` for reporting but deliberately does **not** use `BelongsToLaundry`, because the owner decided complaints are the platform's to handle (Routes / Model).

- **Task 2 of the gap audit — ratings.** «ما رأيك في تجربتك؟» was designed in full in Figma and entirely absent from the code: no table, no API, no screen. Every report before this measured speed and disputes; none could say whether the customer was happy, which is what a laundry is actually judged on (Database / API / Service / Blade).
- **The subject is the laundry; the aspects are stored separately.** That was the owner's decision, but «التوصيل والاستلام» and «مندوب ودود» describe the *driver*, so folding them into one number would mark a laundry down for a late driver. `overall`, `service_quality`, `delivery` and `timing` are four columns — the delivery score exists as data and can be attributed to the driver later with no migration (Database).
- `order_ratings`: **one row per order**, enforced by a unique index rather than a check in code, so a double tap on a slow connection cannot move a laundry's average. `laundry_id` is denormalised so `BelongsToLaundry` scopes it — a laundry owner reads its own verdicts and nobody else's, which is why this screen is granted to the laundry roles unlike the driver and operations reports (Database).
- `POST` / `GET /api/v1/orders/{id}/rating`. The GET is not symmetry: the design puts a «تقييم» button on a completed order, so `can_rate` is served rather than inferred — a button that opens a screen which then refuses is worse than no button (API).
- **Three rules that protect the figure rather than the flow:** only a finished order can be rated (a rating given while the clothes are still at the laundry is a guess that would sit in the average as a verdict); only once, checked under `lockForUpdate` so a race surfaces as a clear refusal rather than a 500 from the unique index; and the laundry is copied from the order, never read from the payload — it is the only field whose value changes somebody else's numbers (Service).
- A skipped aspect stays **null, not zero**. Zero is not a score the five stars can produce, and a 0 in the column would drag every average down while looking like data (Service).

### Fix

- **`roles.type` could not hold `laundry` on any driver but MySQL.** The P1 widening migration used a raw `ALTER` behind a `getDriverName() === 'mysql'` guard, on the belief that `->change()` still needs doctrine/dbal — untrue since Laravel 11. On SQLite the original `enum` becomes a CHECK constraint, so inserting `laundry` failed with "CHECK constraint failed: type": the entire tenancy feature was untestable, and a deploy on any other driver would have broken identically. Added a cross-driver migration converting the column to `varchar(20)`; a string plus the application's own validation also means the next role type is not a schema change at all (Migration).
- **`users.email` stayed NOT NULL on any driver but MySQL**, for the same reason and with the same effect: no test could register a customer. Rewritten to use `->change()` (Migration).
- **`Language::$fillable` omitted `default` and `app_scope`** while `LanguageRequest` validated both, so marking a language as default from the dashboard silently did nothing. MySQL hid half of it by quietly substituting the first enum value for `app_scope` on insert; SQLite refuses, which is how it surfaced. Proven before and after: asking for `default=true` stored `false` (Model).
- **Timestamps were written and compared in different timezones.** `SetTimezone` called `date_default_timezone_set()` per request, so anything writing a timestamp outside the HTTP lifecycle — the queue worker, console commands, seeders, and the recurring-order scheduler planned for P6 — stored a UTC wall-clock string that the next request re-read as Cairo local time, three hours earlier. Concretely, OTP codes were born already expired. Storage and comparison now stay in UTC; `SetTimezone` publishes `app.display_timezone` instead, and `humanDate()` is the single place a stored value is converted for display. The nine dashboard timestamp call sites were routed through it, so displayed times remain local (Middleware / Helper / Blade).
- **Six of the modules I added read the wrong search parameter.** `setupAjaxSearch` sends the term as `query`, which is what the ten pre-existing modules read via `$request->get('query')`; Laundry, LaundryStaff, Service, Item, ItemCategory and Zone read `$request->search`, which was always null, so those six search boxes re-rendered the full list unchanged. Note the controllers cannot read `query` as a property: Symfony's `Request` has a public `$query` holding a ParameterBag (Controllers).
- `CategoryController::search()` ignored the search term entirely, calling `shredData()` while the repository had a `search()` all along. Wired up (Controller / Service).
- Rewrote the stock `ExampleTest`, which failed on every run: it lacked `RefreshDatabase`, so there were no tables, and `/` renders a view whose layout reads the settings and languages tables (Tests).
- Removed a stray `console.log` from `setupAjaxSearch` (Blade).

### Fix
