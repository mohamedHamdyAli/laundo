# تكرار الطلبات — دليل تكامل الموبايل

> **Laundo API v1 · Order Recurrence**
> Base: `/api/v1` · Auth: Bearer (Sanctum, توكن باسم `mobile`) · 9 endpoints · كرون يومي 09:00

العميل يحفظ جدول «كل أسبوع / كل أسبوعين / كل شهر». في يوم الاستحقاق النظام **يسأله**، ولو قال أيوه بيفتحله الويزارد على سلة مملوءة — الطلب اللي يخرج منه هو اللي بيقفل السؤال.

---

## القاعدة الأساسية

**الجدول عمره ما بيعمل طلب لوحده.**

لما ييجي ميعاده، بيفتح **prompt** ويبعت إشعار «محتاج تغسل النهاردة؟» ويستنى.

و«أيوه» كمان **مش بيعمل طلب**. بيرجّع سلة مملوءة، والعميل يراجع القطع ويختار الميعاد وطريقة الدفع في الويزارد العادي — والطلب اللي بيطلع من الويزارد هو اللي بيقفل السؤال. الرفض — أو عدم الرد أصلاً — بيتخطى الدورة دي والجدول يفضل شغال للدورة اللي بعدها.

ده معناه إن الموبايل عنده **كيانين مختلفين**، وكل واحد ليه شاشة:

- **الجداول** — يضيف / يوقف / يستأنف / يلغي
- **الأسئلة المفتوحة** — يراجع السلة ويحجز، أو يتخطى

متعاملش الاتنين كحاجة واحدة.

| --- | --- | --- |

## 2. إدارة الجداول

ست إندبوينتس. كلها بترجّع نفس شكل الـ schedule object ما عدا الحذف.

### `GET /api/v1/recurrences`

كل جداول العميل، الأحدث الأول. **مش paginated** — مصفوفة كاملة في `data`.

```jsonc
{ "key": "success", "status": "success", "msg": "", "code": 200, "data": [
  {
    "id": 7,
    "frequency": "weekly",
    "day_of_week": 1,                    // ISO: 1=Mon … 7=Sun
    "status": "active",                  // active | paused | cancelled
    "service": "غسيل وكي",                // مترجم حسب هيدر lang
    "service_id": 2,
    "pickup_address_id": 15,
    "time_slot": "10:00 AM – 12:00 PM",  // نص جاهز، ممكن يكون null
    "items": [ { "item_id": 4, "qty": 3 }, { "item_id": 9, "qty": 1 } ],
    "next_prompt_on": "2026-09-14"       // null لو ملغي
  }
] }
```

`time_slot` نص معروض مش ID، و `items` فيها الـ IDs بس — من غير أسماء ولا أسعار. لو محتاج تعرض السلة بأسماء، اقرأ الأصناف من `/items` واعمل الربط عندك.

### `POST /api/v1/recurrences`

إنشاء جدول جديد. بيرجّع **201** ونفس شكل الـ object فوق.

| الحقل | | القاعدة |
| --- | --- | --- |
| `service_id` | required | خدمة `status=active` موجودة |
| `pickup_address_id` | required | لازم يكون عنوان العميل نفسه، وإلا **404** |
| `time_slot_id` | nullable | فترة `active`. لو null الطلب هيتعمل من غير فترة محددة |
| `frequency` | required | `weekly` · `biweekly` · `monthly` |
| `day_of_week` | شرطي | 1–7 (ISO). **مطلوب إلا لو** `frequency=monthly` |
| `items` | required | مصفوفة، صنف واحد على الأقل |
| `items[].item_id` | required | صنف موجود |
| `items[].qty` | required | من 1 لـ 999 |
| `starts_on` | nullable | تاريخ **بعد النهاردة** — النهاردة نفسه مرفوض |

```json
{
  "service_id": 2,
  "pickup_address_id": 15,
  "time_slot_id": 3,
  "frequency": "weekly",
  "day_of_week": 1,
  "items": [ { "item_id": 4, "qty": 3 } ]
}
```

**لو مبعتش `starts_on`:** السيرفر بيحسب أول ميعاد — للأسبوعي أقرب يوم بالرقم اللي اخترته **ابتداءً من بكرة** (النهاردة مش بيتحسب أبداً)، وللشهري بعد أسبوع من النهاردة.

**أخطاء:** `422 validation_error` مع `errors` مفاتيحها أسماء الحقول · `404` لو العنوان مش بتاع العميل.

### `PUT /api/v1/recurrences/{id}/pause`

إيقاف مؤقت — `status` يبقى `paused` والكرون يتخطاه. `next_prompt_on` بيفضل زي ما هو.

بيرجّع **200** بالـ object بعد التعديل · **404** لو الجدول مش بتاع العميل.

### `PUT /api/v1/recurrences/{id}/resume`

استئناف — و**بيعيد تثبيت الميعاد في المستقبل**.

جدول واقف شهرين هيرجع بميعاد قديم؛ السيرفر بيقدّمه دورة ورا دورة لحد ما يعدّي النهاردة، فمفيش إشعار بيتبعت لحظة الاستئناف. الـ `next_prompt_on` اللي في الرد هو الصح — اعرضه للعميل بعد الاستئناف.

### `PUT /api/v1/recurrences/{id}/items`

«تحب أخلي دي كمياتك الافتراضية؟» — بعد ما العميل يعدّل السلة في الويزارد.

```json
{ "items": [ { "item_id": 4, "qty": 5 } ] }
```

بيرجّع **200** بالـ schedule object بعد التعديل. **القطع بس** — التكرار واليوم والعنوان هوية الجدول ولسه تغييرها إلغاء وإنشاء من جديد.

نفس حدود الإنشاء: صنف واحد على الأقل، `qty` من 1 لـ 999، أصناف `active`. جدول مش بتاع العميل → **404**. سلة فاضية → **422**.

### `DELETE /api/v1/recurrences/{id}`

إلغاء نهائي. `status=cancelled` و `next_prompt_on=null`.

الصف **مش بيتشال** من الداتابيز، فهيفضل يرجع في `GET /recurrences` بحالة `cancelled` — فلترها في التطبيق لو مش عايز تعرضها. الرد رسالة بس من غير `data`.

**التعديل محدود:** الكميات ليها `PUT …/items` فوق. أي حاجة تانية — التكرار، اليوم، العنوان، الفترة — لسه إلغاء + إنشاء جديد.

## 3. أسئلة الدورة

النص التاني من الفيتشر. الـ prompt هو الشاشة اللي العميل بيرد عليها.

### `GET /api/v1/recurrences/prompts`

الأسئلة اللي لسه **من غير إجابة**، مرتبة بتاريخ الاستحقاق. دي شبكة الأمان لو البوش ماوصلش.

```jsonc
{ … "data": [
  {
    "id": 42,                     // ده اللي بتبعته في confirm/decline
    "recurrence_id": 7,
    "for_date": "2026-09-07",     // يوم الدورة، مش يوم الرد
    "service": "غسيل وكي",
    "question": "محتاج تغسل النهاردة؟"
  }
] }
```

**مفيش انتهاء صلاحية.** prompt محدش رد عليه بيفضل هنا للأبد، فممكن يتجمع أكتر من واحد. اعرض `for_date` دايماً، ولو التاريخ عدّى اعرضه كسؤال قديم أو اخفيه.

ولاحظ إن الليستة دي بقت كمان **ليستة سلال متروكة**: العميل اللي ضغط «أيوه» وساب الويزارد سؤاله لسه هنا. ده مقصود — أحسن من إننا نحسبه رد وهو ما طلبش حاجة.

### `POST /api/v1/recurrences/prompts/{id}/confirm`

«أيوه» — بيرجّع **سلة مملوءة**، مش طلب. من غير body.

```jsonc
{
  "prompt_id": 42,
  "recurrence_id": 7,
  "for_date": "2026-09-07",       // الدورة، وده اليوم اللي الويزارد يفتح عليه
  "service_id": 2,
  "pickup_address_id": 15,
  "delivery_address_id": 15,      // الجدول فيه عنوان واحد
  "time_slot_id": 3,              // ممكن null
  "items": [ { "item_id": 4, "qty": 3 } ]
}
```

خد ده، اعرض «نفس القطع اللي المرة اللي فاتت؟»، وكمّل في الويزارد العادي.

**مفيش أي أثر جانبي.** الـ prompt بيفضل مفتوح، والنداء مرتين بيرجّع نفس السلة. ده مقصود: العميل اللي يفتح السلة ويقفل التطبيق لازم يتسأل تاني.

**السؤال بيتقفل بس** لما `POST /orders` يوصل ومعاه `prompt_id` — تحت مباشرة.

**أخطاء:** `400` لو اتردّ عليه قبل كده · `404` prompt مش بتاع العميل.

### `POST /api/v1/orders` — ومعاه `prompt_id`

الويزارد العادي بالظبط، بحقل واحد زيادة:

```jsonc
{
  "prompt_id": 42,                // ده اللي بيقفل السؤال
  "service_id": 2,
  "pickup_address_id": 15,
  "items": [ { "item_id": 4, "qty": 5 } ],   // الكميات بعد تعديل العميل
  "pickup_slot_id": 7,
  "pickup_date": "2026-09-08",
  "payment_method": "cash",
  "accepts_review_terms": true
}
```

في transaction واحدة: الطلب بياخد `recurrence_id` بتاع الجدول، والـ prompt بيتقفل بـ `answer=confirmed` و `order_id`.

| | |
| --- | --- |
| **اللي بيقرره العميل** | السلة، الميعاد، الفترة، طريقة الدفع، الكوبون، ملاحظات السواق، الصور |
| **اللي بيقرره السيرفر** | الربط بالجدول — بيتقرا من الـ prompt، **مش** من الريكوست |

**أخطاء:** `404` prompt مش بتاع العميل · `400` اتردّ عليه قبل كده · `422` باقي أخطاء الويزارد زي أي طلب.

**سعة الفترة بتتطبق عادي دلوقتي.** كانت متجاوز عنها في التكرار لأن مفيش شاشة يختار منها فترة تانية — بقى فيه، فالاستثناء اتشال. فترة مليانة → `422` على `pickup_slot_id`، والسؤال يفضل مفتوح.

### `POST /api/v1/recurrences/prompts/{id}/decline`

«مش محتاج» — تخطي الدورة دي. **الجدول مابيتمسّش** والسؤال هيتكرر في الدورة الجاية.

رد رسالة بس من غير `data`. لو اتردّ عليه قبل كده: `400`.

## 4. الإشعار

بيتبعت على كل توكن مسجّل للعميل عبر `POST /devices`. قنوات الحدث: `database` (قائمة الإشعارات جوه التطبيق) و `push`.

```jsonc
// FCM — كل القيم strings
{
  "notification": {
    "title": "محتاج تغسل النهاردة؟",
    "body": "طلبك المتكرر مستحق النهاردة…"
  },
  "data": {
    "event": "recurrence_prompt",
    "prompt_id": "42"
  }
}
```

- **افتح على الـ prompt مباشرة.** افرز على `data.event === "recurrence_prompt"` وخد `prompt_id`. الحدث كمان بيحمل `url` داخلياً بقيمة `/recurrences/prompts/{id}` لو حابب تستخدم deep link موحّد.
- **ده إشعار transactional.** يعني بيعدّي حتى لو العميل قافل الإشعارات من «الإشعارات» في الإعدادات — لأن الفيتشر كلها هي السؤال ده. وفيه rate limit على مستوى الموضوع الواحد، فمتقلقش من تكرار.
- **مفيش جهاز مسجّل = مفيش سؤال.** لو العميل مسجّلش توكن، الـ prompt بيتفتح في الداتابيز والبوش بيتخطى. عشان كده **لازم** تنادي `GET /recurrences/prompts` عند فتح التطبيق، مش تعتمد على البوش لوحده.

## 5. نقاط لازم تاخد بالك منها

دي اللي بتتفلت في التنفيذ وبتترجم بعدين على إنها باج في الـ API.

1. **الجدول مش اشتراك.** متعرضهوش على إنه «هيتم استلام غسيلك كل اتنين». الوصف الصح: «هنسألك كل اتنين». جدول اتسأل 8 مرات واترد عليه مرتين ده تذكير أسبوعي، مش التزام.
2. **`confirm` مش بيخلص حاجة.** لو التطبيق وقف عنده، العميل يكون جاوب وما اتعملش طلب. الخطوة اللي بتخلص هي `POST /orders` بالـ `prompt_id`.
3. **الرد مرة واحدة بس.** بعد ما الطلب يتعمل، `confirm` و `decline` وإعادة `POST /orders` بنفس الـ `prompt_id` كلهم `400`. اقفل الشاشة وشيل الـ prompt من الليستة محلياً.
4. **مفيش سعر في الجدول.** الجدول بيحفظ *نية* مش فاتورة. عشان تعرض تقدير في شاشة المراجعة، نادي `POST /orders/quote` بالسلة اللي رجعت من `confirm`.
5. **عنوان التسليم بيفتح على عنوان الاستلام.** الجدول فيه عنوان واحد، فالسلة بترجع الاتنين نفس القيمة — لكن الويزارد يقدر يغيّر عنوان التسليم عادي، عكس السلوك القديم.
6. **التعديل جزئي.** الكميات ليها `PUT …/items`. التكرار واليوم والعنوان = `DELETE` ثم `POST` من جديد، وده بيصفّر الـ `id`.
7. **السلة اللي في الطلب مش بتتحفظ لوحدها.** لو العميل غيّر الكميات، الجدول يفضل على القديمة. اسأله «تحب أخلي دي الافتراضية؟» ونادي `PUT …/items` لو قال أيوه.
8. **كل التواريخ `YYYY-MM-DD` بتوقيت السيرفر.** `next_prompt_on` و `for_date` تواريخ مجردة من غير وقت ولا timezone. متحوّلهاش لـ UTC ولا تطبّق عليها إزاحة.
9. **`day_of_week` نظام ISO.** 1 = الاثنين … 7 = الأحد. لو الـ picker عندك بيبدأ بالأحد لازم تحوّل — غلطة الإزاحة بيوم هنا معناها إن العميل هيتسأل في يوم غير اللي اختاره.
10. **الشهري من غير يوم أسبوع.** لما `frequency=monthly` اخفي مختار اليوم خالص ومتبعتش `day_of_week` — الشهري بيتكرر من تاريخ بدايته.
11. **`starts_on` النهاردة مرفوض.** القاعدة `after:today` مش `after_or_equal`. لو الـ date picker بيسمح بالنهاردة هترجع `422`.
12. **الملغي بيفضل في الليستة.** `GET /recurrences` بيرجّع الثلاث حالات. فلتر `cancelled` بنفسك أو اعرضها في قسم منفصل.
13. **الاستئناف مش بيسأل فوراً.** بعد `resume` اعرض `next_prompt_on` اللي رجع في الرد بجملة صريحة: «هنسألك يوم كذا».
14. **ابعت هيدر `lang`.** اسم الخدمة ونص الرسائل بيترجموا حسبه. من غيره بتاخد اللغة الافتراضية للنظام مش لغة التطبيق.

## 6. شكل الرد والأخطاء

نفس الـ envelope في كل إندبوينتس الـ API — مفيش استثناء للتكرار.

```json
{
  "key": "success",
  "status": "success",
  "msg": "تم حفظ جدول التكرار.",
  "code": 201,
  "data": {}
}
```

```json
{
  "key": "validation_error",
  "status": "error",
  "msg": "Invalid data send",
  "code": 422,
  "errors": { "day_of_week": ["…"] }
}
```

**افرز على `key` مش على `status`.** الـ `status` متولّد من الـ `code` وبيقول «نجح ولا لأ» بس؛ الـ `key` هو اللي بيقول *أنهي* نتيجة. والاتنين بيوافقوا HTTP status الحقيقي دايماً.

| Code | key | يحصل امتى في التكرار |
| --- | --- | --- |
| 200 | `success` | قراءة، `confirm` (السلة)، تعديل الكميات، إيقاف، استئناف، إلغاء، تخطي |
| 201 | `success` | إنشاء جدول، إنشاء طلب |
| 400 | `fail` | prompt اتردّ عليه قبل كده |
| 404 | `not_found` | جدول / prompt / عنوان مش بتاع العميل |
| 422 | `validation_error` | body ناقص أو قيمة غلط في الإنشاء |
| 401 | `not_auth` | توكن ناقص أو منتهي |
