## اللي لازم تغيّروه في التطبيق

ده الجزء العملي. الباقي شرح.

### ١. بدّلوا كل قراءة تاريخ على الحقل الـ `_iso`

أي مكان بتقروا فيه `due_at` أو `started_at` أو `completed_at` وبتحاولوا تبارسوه
أو ترتبوا بيه أو تحسبوا منه فرق — بدّلوه بالتوأم بتاعه.

```dart
// قبل — دي جملة، مش تاريخ
final due = task['due_at'];          // "خلال ساعتين" / "in 2 hours"

// بعد
final due = task['due_at_iso'] != null
    ? DateTime.parse(task['due_at_iso'])   // 2026-09-13T18:00:00+03:00
    : null;                                // معناها: مفيش ميعاد متفق عليه
```

`due_at` القديم **سايبينه زي ما هو** لو عايزين تعرضوه كنص جاهز. بس متبارسوهوش.

### ٢. الماب: استعملوا `destination_location` في الليستة

مبقاش لازم تفتحوا تفاصيل التاسك عشان تعرفوا هي رايحة فين.

```dart
final point = task['destination_location'];   // {lat, lng} أو null
if (point != null) {
  marker(point['lat'], point['lng']);
} else {
  showAddressTextOnly(task['destination']);
}
```

**مهم:** `null` معناها محدش حط الدبوس. **متحطوش (0, 0)** — دي نقطة في وسط
المحيط الأطلنطي.

### ٣. الـ pagination: اقروا `meta` مش `msg`

ده على الأرجح اللي كان بيلغبطكم أكتر حاجة. `msg` كانت بترجع صفحة HTML كاملة.

```dart
// كان بيرجع: msg: "<nav class=\"d-flex justify-items-center...\">..."
// بقى:       msg: ""

final meta = body['meta'];
meta['current_page'];   // 1
meta['per_page'];       // 15
meta['has_more'];       // true / false  ← ده اللي يوقف الـ infinite scroll
meta['total'];          // 42
meta['last_page'];      // 3
```

قبل كده `meta` كانت `{}` فاضية **دايمًا**، فلو كنتوا بتتصرفوا حواليها — دلوقتي
فيها اللي محتاجينه.

### ٤. شيلوا أي workaround عملتوه لترتيب التاسكات

الليستة بقت مستقرة. لو كنتوا بترتبوا محليًا بعد ما توصل، الترتيب بتاعنا بقى:
أقرب ميعاد ← اللي من غير ميعاد في الآخر ← رقم الرجل ← الـ id.

### ٥. `steps[].reached` بقت موثوقة

لو كنتوا بتشتغلوا حواليها في شاشة التتبّع، شيلوا الـ workaround. وخدوا بالكم:
ممكن ترجع `reached: true` و `at: null` مع بعض — اقرا [البند ٣](#٣-تاسكات-خلصت-بترجع-بحالة-غير-مكتملة).

## البنود بالتفصيل

### ١. تاريخ ووقت التسليم

#### المشكلة كانت أكبر من اللي اتبلّغ عنه

إنتوا قلتوا «بيرجع null أحيانًا». الحقيقة أوسع: **إنتوا مكنتوش بتاخدوا تاريخ
أصلاً، ولا مرة**. الحقل كان بيترسل كده:

```php
'due_at' => humanDate($task->due_at)
```

و `humanDate()` من غير format بتنادي `diffForHumans()` — يعني اللي كان واصلكم
«منذ ساعتين» / «in 2 hours». نص، مترجم حسب الـ `lang` header، **وبيتغيّر كل ما
تطلبوا الـ endpoint**. مش قابل للبارس ولا للترتيب ولا للمقارنة.

ومكنش في `due_at` بس: **١٦ حقل وقت في ٧ كنترولرز** كانوا كده، وفي نفس الوقت
الـ API كان مستعمل **تلات فورماتات مختلفة** (ISO 8601 في ٥ أماكن، `Y-m-d` في
٨، والنص النسبي في ١٦). عشان كده سؤالكم كان «أكدولنا على الـ format وثباته» —
سؤال في محله تمامًا.

#### الحل

`isoDate()` جديدة في `app/Helpers/Helpers.php`، وكل حقل نسبي بقى له توأم بنفس
الاسم `+ _iso`:

| الـ endpoint | الحقول الجديدة |
|---|---|
| `GET /api/v1/driver/tasks` | `due_at_iso` |
| `GET /api/v1/driver/tasks/{id}` | `due_at_iso` · `started_at_iso` · `completed_at_iso` |
| `GET /api/v1/driver/tasks/history` | `due_at_iso` · `started_at_iso` · `finished_at_iso` |
| `GET /api/v1/driver/summary` | `current_task.due_at_iso` |
| `GET /api/v1/driver/earnings` | `at_iso` |
| `GET /api/v1/orders` · `GET /api/v1/orders/{id}` | `created_at_iso` |
| `GET /api/v1/orders/{id}/track` | `steps[].at_iso` |
| `GET /api/v1/orders/{id}/review` | `confirmed_at_iso` |
| `GET /api/v1/orders/{id}/queries` | `asked_at_iso` · `answered_at_iso` |
| `GET /api/v1/orders/{id}/payments` | `paid_at_iso` |
| `GET /api/v1/orders/{id}/refunds` | `requested_at_iso` · `settled_at_iso` |
| `GET /api/v1/notifications` | `at_iso` |
| `GET /api/v1/wallet/transactions` | `at_iso` |

الشكل: `2026-09-13T18:00:00+03:00` — ISO 8601 **بالـ offset**، فمحدش محتاج
يخمّن الـ timezone بتاعة السيرفر.

#### طلب الـ `required` — مترفض، ودي الأسباب

طلبتوا: «لو فيه تاسك مش متسجل له تاريخ تسليم، لازم يترفض وقت الإنشاء». ده
هيكسر فلو شغّال دلوقتي. `due_at` بيبقى `null` في **حالتين مشروعتين**:

1. **أوردر اتعمل من غير شباك تسليم.** `delivery_date` و `delivery_slot_id`
   الاتنين `nullable` في `app/Http/Requests/Api/V1/OrderRequest.php` وفي الـ
   migration. العميل ممكن يحجز الاستلام بس ويسيب التسليم.

2. **رِجل اتأجّلت.** لما سواق يأجّل رجل، `TaskService::clearSchedule()`
   **بيمسح التاريخ والـ slot عن قصد** وبيبعت للعميل يحجز ميعاد جديد. ده مش
   باج، ده الفلو.

يعني `null` هنا **حالة حقيقية اسمها «لسه مفيش ميعاد متفق عليه»**، مش بيانات
ناقصة. الـ API بقى بيقولها صراحة بدل ما يبعت null صامت.

**اللي محتاجينه من التطبيق:** اعرضوا «لم يُحدَّد بعد» بدل ما تعرضوا فراغ أو
تحاولوا تخمّنوا تاريخ.

> لو الشركة عايزة فعلاً تمنع إنشاء أوردر من غير تاريخ تسليم — ده **قرار منتج**
> مش باج، وممكن ننفّذه بسرعة. بس محتاج قرار من صاحب المنتج الأول، وهيحتاج نقرر
> إيه اللي يحصل للرجل المتأجّلة.

### ٢. الإحداثيات

#### اللي لقيناه

- **تفاصيل التاسك** كان فيها `address.lat` و `address.lng` — بس **للرجل اللي
  عند العميل بس**.
- **ليستة التاسكات** مكنش فيها إحداثيات خالص، `destination` كنص شارع وبس.
- **رجلتين المغسلة** (تسليم للمغسلة، واستلام منها) كانوا بيرجعوا `null`
  **مكتوبة بالإيد في الكود**:

  ```php
  : ['street' => $order?->laundry?->address, 'lat' => null, 'lng' => null],
  ```

  رغم إن `laundries.lat` و `laundries.lng` أعمدة موجودة ومليانة. يعني **نص
  الرحلة مكنش ليه ماب أصلاً**.

  وكمان لو كنا شيلنا الـ null دي لوحدها مكنش هيحصل حاجة: الـ eager load كان
  `laundry:id,name,address,phone` من غير `lat,lng`، والـ constrained eager
  load بيرجع `null` في صمت لأي عمود مش مذكور. الاتنين اتظبطوا.

#### الحل

ميثود واحدة جديدة `TaskType::coordinatesFor()` بتردّ على **الأربع رجل**، جنب
`destinationFor()` اللي بيرد بالشارع — الاتنين بيوصفوا نفس المكان فمينفعش
يكونوا في مكانين.

```jsonc
// GET /api/v1/driver/tasks  →  data[]
{
  "destination": "شارع التحرير، الدقي",
  "destination_location": { "lat": 30.0561, "lng": 31.2003 },   // جديد
  "due_at": "خلال ساعتين",
  "due_at_iso": "2026-09-13T18:00:00+03:00"                     // جديد
}
```

```jsonc
// GET /api/v1/driver/tasks/{id}  →  data.address
// دلوقتي بيرجع lat/lng في الأربع رجل، المغسلة كمان
{ "street": "...", "lat": 30.0444, "lng": 31.2357 }
```

```jsonc
// GET /api/v1/orders/{id}/track  →  data
{
  "driver":            { "location": { "lat": 30.05, "lng": 31.21 } },  // النقطة الحية
  "pickup_location":   { "lat": 30.0561, "lng": 31.2003 },              // جديد
  "delivery_location": { "lat": 30.0561, "lng": 31.2003 }               // جديد
}
```

النقطة الحية بتاعة المندوب كانت بتتحرك على ماب مالهاش أي مرجع — العميل مكنش
يعرف العربية قربت من شارعه ولا لأ.

#### ملحوظة مهمة على الـ endpoint اللي قصدتوه

`GET /api/v1/orders/{id}/track` هو endpoint **العميل**، مقفول على أوردراته هو
(`$request->user()->orders()`). **توكن السواق بياخد منه 404.**

لو تطبيق السواق بينادي عليه فده سوء فهم عندنا أو عندكم — قولولنا وهنظبطه. عشان
كده غطّينا الاحتمالين: الإحداثيات اتضافت في **تاسكات السواق** (ليستة وتفاصيل)
**و** في **الـ track بتاع العميل**.

### ٣. تاسكات خلصت بترجع بحالة غير مكتملة

#### اللي لقيناه

مقدرناش نكرّرها في المسار الطبيعي — جدول الانتقالات في `OrderStatus` خطّي
ومفيش حالة بتتخطّى، ومفيش أي كود بيغيّر حالة الأوردر من غير ما يعدّي على الـ
state machine (اتأكدنا بالبحث). يعني في المسار العادي كل خطوة بيتكتبلها صف.

**بس** `OrderTimeline` كان بيقرّر كل خطوة **من صفها هي بس**:

```php
'reached' => $log !== null,
```

من غير أي ضمان تصاعدي. فصف واحد ناقص لأي سبب — تعديل يدوي على الداتابيز، أو
أوردر قديم اتعمل قبل ما خطوة تتضاف للقائمة — والخطوة دي بتفضل `false`
**للأبد**، حتى والأوردر واصل `delivered`.

ده بالظبط اللي إنتوا شايفينه: الخطوة الأخيرة `true` وواحدة في النص `false`.

#### الحل

```
قبل:  [✓] [✓] [✗] [✓] [✓] [✓] [✓] [✓]    ← بيتقرا إن فيه حاجة اتخطّت
بعد:  [✓] [✓] [✓] [✓] [✓] [✓] [✓] [✓]
```

خطوة ورا خطوة متعدّاة بقت بتتحسب متعدّاة. **بس `at` و `at_iso` بيفضلوا `null`**
في الحالة دي — إحنا عارفين إنها حصلت، مش عارفين **إمتى**، واختراع وقت على شاشة
تتبّع أسوأ من خانة فاضية.

اللي فعلاً محصلش يفضل `false` طبعًا.

**اللي محتاجينه من التطبيق:** لو `reached: true` و `at: null` مع بعض، اعرضوا
الخطوة كمتعدّاة من غير وقت.

### ٤. ترتيب التاسكات

#### اللي لقيناه

الليستة **مكنتش عشوائية**، كانت **غير مستقرة** — وده فرق مهم. الـ query كان:

```sql
ORDER BY due_at IS NULL, due_at
```

يعني: الأقرب ميعاد الأول، واللي من غير ميعاد في الآخر. **بس مفيش فاصل تعادل.**

والتعادل هو الحالة الشائعة هنا لسببين: الأربع رجل بتاعة الأوردر الواحد
بيشاركوا نفس الشباك الزمني، والرجل اللي اتأجّلت مالهاش ميعاد خالص (البند ١).
MySQL مبتوعدش إنها ترجّع الصفوف المتعادلة بنفس الترتيب مرتين، فذيل الليستة كان
بيتخلط بين الطلبات.

**ومع الـ pagination ده أسوأ:** التاسك ممكن يظهر في صفحة ١ وصفحة ٢ مع بعض، أو
ميظهرش في ولا واحدة فيهم.

#### الحل

`OrderTask::scopeInDueOrder()`:

```sql
ORDER BY due_at IS NULL,   -- اللي من غير ميعاد في الآخر
         due_at ASC,       -- الأقرب ميعاد الأول
         sequence ASC,     -- بعدين رقم الرجل (١ استلام … ٤ تسليم)
         id ASC            -- بعدين الأقدم
```

المعيار ده **متأكّد عليه** حسب طلبكم في البند ٤. معناه العملي إن عند التعادل
الكامل، كل رجل الاستلام بتيجي الأول وبعدين رجل التسليم — وده اللي سواق بيخطّط
خط سير بيحتاجه.

والـ history أخد نفس المعاملة على `updated_at`، لأن مجموعة رجل بتخلص في نفس
اللحظة بتشارك نفس الثانية.

### ٥. حاجة مكنتش في ليستتكم — وعلى الأرجح كانت بتوجعكم

كل endpoint بيرجع list في الـ API كان بيحط **صفحة HTML كاملة** في `msg`:

```
msg: "<nav class=\"d-flex justify-items-center justify-content-between\">
        <div class=\"d-flex justify-content-between flex-fill d-sm-none\">
          <ul class=\"pagination\">…"
```

السبب: الهيلبر كان معرّف `successReturnPaginated($paginator, $msg)` وكل مواضع
النداء مكتوبة `($items, $paginator)` — فالـ paginator كان بيقع في خانة الرسالة،
وPHP بتحوّله لنص عن طريق `__toString()` اللي **بيرسم الـ Blade pagination
view**.

ونتيجة تانية: **`meta` كانت `{}` فاضية في كل list في الـ API** — لا `total` ولا
`has_more` ولا `last_page`.

الاتنين اتصلّحوا. الـ endpoints المتأثرة:

`GET /api/v1/orders` · `GET /api/v1/notifications` ·
`GET /api/v1/wallet/transactions` · `GET /api/v1/driver/tasks` ·
`GET /api/v1/driver/tasks/history`

> ملحوظة: الـ HTML كان بيبان **بس لما يكون فيه أكتر من صفحة** — Laravel مبترسمش
> حاجة لو الليستة صفحة واحدة. عشان كده كان بيظهر ويختفي، وصعب تكرّره.

## حاجات محتاجين ردكم عليها

1. **تطبيق السواق بينادي على `GET /api/v1/orders/{id}/track`؟** لو أيوة، ده
   endpoint العميل ومقفول على توكن السواق (بيرجع 404). قولولنا عشان نقرر: نعمل
   نسخة للسواق، ولا التطبيق يستعمل `GET /api/v1/driver/tasks/{id}`؟

2. **عايزين `due_at` القديم (النص النسبي) يفضل؟** لو التطبيق بقى بيعتمد على
   `due_at_iso` بس، ممكن نشيل النص النسبي في v2 ونخفّف الـ payload.

3. **قرار الـ `required` على تاريخ التسليم** — مستنيين رد صاحب المنتج، مش قرار
   تقني.

---

## فيه باج تاني لقيناه ومسيّبينه بقرار

**ليستة تاسكات السواق بتعمل query لكل صف** عشان تحسب `can_start` —
`predecessorComplete()` بيعمل `SELECT EXISTS` لكل تاسك. ٨ تاسكات = ٦ queries
زيادة.

مالوش علاقة بالإحداثيات (دي batched في ٣ queries، وفيه تست بيثبت ده)،
ومسيّبينه لأنه خارج نطاق اللي طلبتوه ولمسه بيمسّ منطق بدء المهام في أماكن
تانية. **لو الليستة بطيئة عندكم قولولنا** — يتصلّح في وقت قصير.

## التحقق

- **٧ تستات جديدة** بتغطي البنود الأربعة.
- **كل فيكس اترجّع وشوفنا التست بيقع** قبل ما نرجّعه — تست عمره مفشل متثبتش إنه
  بيختبر حاجة.
- السويت كاملة: **١١٨٥ تست / ٣٨٢٠ assertion**، PHPStan نضيف.
- التوثيق اتحدّث في الـ Postman collection وفي `docs/api-reference.html` —
  الوصف بتاع كل endpoint فيه الحقول الجديدة وشكلها.

> حتى لما ضفنا الاسم اللي انتوا بتقروه جنبه. النسخة اللي عندكم دلوقتي هتفضل
> شغالة، وتنقلوا على الجديد على راحتكم.

## ⚠️ الأول: اتأكدوا من نسخة السيرفر اللي بتختبروا عليها

في تقريركم على `/track` مكتوب:

> "The endpoint documentation currently states there is no phone number **by
> policy rather than by omission**"

**الجملة دي بايتة.** `driver.phone` اتضاف في **٣ سبتمبر** (كوميت `74a4001`)،
و`steps[].at_iso` اتضاف في **١٣ سبتمبر** (كوميت `0c56987`) — يعني يومين قبل
تقريركم.

يعني على الأغلب انتوا بتختبروا على بيلد أقدم، ونص البند الرابع كان موجود عندكم
أصلاً. **من فضلكم اتأكدوا من النسخة المنشورة قبل ما نفتح تذاكر تانية** — ووصف
الـ Postman اللي اقتبستوا منه الجملة دي اتحدّث في الملف ده.

## ١. `GET /recurrences/prompts` — الجدولة الملغية كانت لسه بتسأل

### السبب الأول اللي قلتوه: صح ✅

`RecurrenceController::pendingPrompts()` كان بيفلتر على `whereNull('answer')`
وعلى صاحب الجدولة **وبس** — مفيش أي فلتر على حالة الجدولة نفسها.
و`RecurrenceService::cancel()` كان بيغيّر الجدولة ومش بيلمس أسئلتها المفتوحة.

يعني كل سؤال اتسأل قبل الإلغاء كان بيفضل مفتوح للأبد على جدولة عمرها ما هترجع
تشتغل. ده بالظبط الـ Tuesday اللي بيرجع.

**اتصلّح في حتتين:**

1. **الإلغاء بيقفل أسئلته** في نفس الترانزاكشن — `answer = 'cancelled'`.
   بتتقفل **مش بتتمسح**: الصف هو سجل إننا سألنا، وطلب اتعمل من دورة قديمة لسه
   مشاور على واحد. (محتاج migration — العمود كان enum من قيمتين بس.)
2. **الليستة بتفلتر على `recurrence.status = active`** — ودي اللي بتغطي
   الموقوفة (paused) كمان، من غير ما تضيّع سؤال جدولة هترجع تشتغل. جدولة موقوفة
   **مبتسألش وهي موقوفة**، والاستئناف بيرجّع السؤال.

### السبب التاني اللي قلتوه: غلط ❌

> "the decline is not persisted against `(recurrence_id, prompted_for)`"

**الـ decline بيتخزّن فعلاً.** `decline()` بيكتب `answer = 'declined'`، والليستة
بتستبعد أي صف `answer` مش null، و`openPrompt()` محمي بـ unique index على
`(recurrence_id, prompted_for)` وبيحرّك الجدولة للدورة اللي بعدها. **مستحيل نفس
الدورة تتسأل تاني.**

ضفنا تست بالاسم ده — `a_declined_cycle_is_never_asked_again` — بيرفض الدورة،
يشغّل الـ scheduler تاني، ويتأكد إن نفس `prompted_for` مرجعش.

**اللي كنتوا شايفينه هو السبب الأول.** الجدولة الملغية كانت بترجّع أسئلتها،
واللي بيرجع مش نفس السؤال اللي رفضتوه — ده سؤال تاني على نفس الجدولة.

### الحقول اللي كانت بأسماء مختلفة عندكم

دي حاجة مانتبهناش ليها ومكنتش في تقريركم كسؤال، بس واضحة من اللي بتقروه:

| انتوا بتقروا | إحنا كنا بنبعت | دلوقتي |
|---|---|---|
| `prompted_for` | `for_date` | **الاتنين** |
| `next_run_on` | `next_prompt_on` | **الاتنين** |
| `is_paused` | مش موجود | ✅ اتضاف |
| `status_label` | مش موجود | ✅ اتضاف (مترجَم بلغة الهيدر) |
| `time_slot_id` | `time_slot` نص بس | ✅ الاتنين |
| `pickup_address` ككائن | `pickup_address_id` بس | ✅ `{id, label, line}` |
| prompt: `items[]`, `pickup_address_id` | مش موجودين | ✅ اتضافوا |

وطلبكم للـ debugging اتعمل: كل صف prompt فيه دلوقتي `status` و`recurrence_status`.

  `GET /orders/{id}` و`POST /orders/quote` بيرسموه — عندكم كود بيقراه أصلاً.

## ٣. `POST /orders/{id}/reschedule` — كان شغال صح من الأول

> "Requested behaviour (to confirm / fix)"

**اتأكدنا من الكود: كل اللي طلبتوه كان محقّق بالفعل.**
`RescheduleService::reschedule()` بيعدّل **نفس صف الأوردر** — `forceFill` على
`pickup_slot_id` / `pickup_date` أو نظيرهم في التسليم — ويرجّع `$order->fresh()`.

- ❌ مفيش صف أوردر جديد ومفيش كود جديد. **ولا مرة.**
- ✅ `GET /orders/{id}` بعدها بيوري التاريخ والنافذة الجديدة.
- ✅ `needs_new_time` بتبقى `false`.

ضفنا تست بالاسم — `rescheduling_rebooks_the_same_order_and_returns_the_booking`
— بيتأكد من الـ `id` والـ `code` وإن عدد الأوردرات فضل واحد.

**اللي اتغيّر فعلاً حاجتين:**

**الرد بقى يحمل الحجز** زي ما طلبتوا بالظبط:

```json
{
  "id": 41, "code": "ORD-1234", "leg": "pickup",
  "date": "2026-09-17",
  "time_slot": { "id": 2, "from": "09:00:00", "to": "12:00:00", "label": "09:00 – 12:00" },
  "needs_new_time": false,
  "status": "awaiting_pickup", "status_label": "في انتظار الاستلام"
}
```

**والـ GET بقى بنفس شكل `GET /time-slots`** — الحالة الخاصة اللي عندكم تتشال:

```json
{
  "needs_new_time": true, "leg": "pickup",
  "date": "2026-09-17", "current_date": null,
  "slot_id": null, "current_slot_id": null,
  "slots": [{
    "id": 2, "from": "09:00:00", "to": "12:00:00",
    "label": "09:00 – 12:00", "applies_to": "both",
    "capacity": 20, "remaining": 18, "is_full": false
  }]
}
```

`remaining` و`is_full` بيترسلوا **دايماً** دلوقتي. السعة بتتحسب على `?date=` لو
بعتّوها، وإلا على تاريخ الرجل نفسها، وإلا على النهاردة — فمفيش حالة «يوم مجهول»
تاني. و**`remaining: null` يعني نافذة من غير سقف** («خد راحتك») مش «مش عارفين» —
`0` هي «اختار غيرها». الاتنين لازم يترسموا مختلفين.

## ٤. `GET /orders/{id}/track`

### اللي كان موجود قبل تقريركم بيومين

`driver` كارت كامل · `driver.phone` (من ٣ سبتمبر) · `driver.location` ومعاها
`updated_at` · `driver.rating` · `driver.image` · `pickup_location` ·
`delivery_location` · `steps[].at_iso` (من ١٣ سبتمبر).

لو دول راجعين `null` عندكم **فده نسخة السيرفر**، مش الحقول.

### اللي اتضاف النهاردة ✅

**`driver.leg`** — وده أهم بند عندكم وانتوا محقّين فيه تماماً:

> "the app cannot say whether the driver is coming to collect or to deliver —
> this is the one that matters most"

كنا بنبعت `role` **مترجَم** بس، فأي تبديل عليه هو تبديل على لغة الطلب. دلوقتي:

```json
"driver": {
  "role": "مندوب الاستلام",          // نص للعرض — لا تبدّل عليه
  "leg": "pickup",                    // pickup | delivery  ← بدّل على ده
  "task_type": "pickup_from_customer",// الرجل الخام من الأربعة
  "photo": "https://…",               // = image، بالاسم اللي بتقروه
  "image": "https://…"
}
```

`leg` بيجمع الأربع رجل في ناحيتين، لأن العميل واقف على طرف واحد بس: يا هدومه
رايحة يا جاية.

**`delivery_address` و`pickup_address`** — البابين كعناوين مقروءة جنب
الإحداثيات:

```json
"pickup_address":   { "id": 9, "label": "البيت", "line": "...", "lat": 30.0, "lng": 31.0 },
"delivery_address": { "id": 9, "label": "البيت", "line": "...", "lat": 30.0, "lng": 31.0 }
```

(`pickup_location` و`delivery_location` فضلوا مكانهم كـ`{lat, lng}`.)

**`eta_iso`** — اقرا القسم اللي تحت قبل ما تستعملوه:

```json
"eta_iso": "2026-09-17T09:00:00+00:00",
"eta_minutes": 25,
"eta_label": "خلال ٢٥ دقيقة",
"eta_window": { "from": "...", "to": "...", "label": "09:00 – 12:00" },
"eta_source": "time_slot"
```

**`delivery_method`** — موجود، بس اقرا القسم اللي تحت عن مفرداته.

### ٤ب. `delivery_method` — المفردات اللي طلبتوها مش موجودة في المنظومة

طلبتوا:

```json
"delivery_method": "home_delivery" | "pickup_point" | "..."
```

**مفيش في Laundo نقط استلام، ولا لوكرز، ولا فروع — ولا حاجة من دول في الداتابيز
ولا في لوحة التحكم ولا في دورة حياة الطلب.** الـ `delivery_method` عندنا اتعمل
لسؤال تاني خالص: **إزاي** الهدوم تتسلّم عند الباب.

القيمتين الوحيدتين هما:

| القيمة | معناها |
|---|---|
| `door` | يتسلّم باليد للعميل |
| `leave` | يتساب عند الباب |

وبعتنا معاها `delivery_method_label` مترجَم بلغة الـ `lang` header زي ما طلبتوا.

**لو الشاشة عندكم فيها فعلاً اختيار «استلام من فرع»** فده مش حقل ناقص — ده
فيتشر مش موجود، ولازم يتفتح مع صاحب المنتج الأول. قولولنا لو ده الحال.

---

### ٤ج. `eta_iso` — بعتناه، بس اعرفوا هو إيه بالظبط

بعتنا `eta_iso` زي ما طلبتوا، **بس لازم تعرفوا مصدره**:

> **ده بداية النافذة المحجوزة، مش وقت وصول محسوب.**

**مفيش في المشروع كله أي حساب ETA** — لا مزوّد routing، ولا distance matrix،
ولا طابور محطات للسواق. لو اخترعنا رقم من موقع السواق الحالي وخط مستقيم، هيبقى
وعد مش قادرين نلتزم بيه، على الشاشة اللي العميل قاعد يبص فيها وهو مستني. ووعد
اتكسر بخمس دقايق أسوأ من نافذة اتحافظ عليها.

فاللي بنبعته هو **النافذة اللي العميل اتوعد بيها فعلاً** — السلوت المحجوز للرجل
اللي في الطريق، في تاريخها. ده التزام الشغل عامله أصلاً والـ dispatch شغال عليه.

- `eta_iso` = **بداية** النافذة (عشان يبقى فيه لحظة واحدة تعدّوا عليها).
- `eta_window` = الطرفين، عشان الشاشة تقول «بين ٩ و١٢» بدل ما تدّعي دقيقة.
- `eta_minutes` **بيقف عند صفر** لما النافذة تكون فتحت — «في أي لحظة»، مش
  «متأخر ٢٠ دقيقة». عدّاد بالسالب على شاشة انتظار العميل بيقراه تأخير.
- `eta_source: "time_slot"` بيقول ده مصدره صراحة، عشان متضطروش تستنتجوا.
- **كله `null`** لما مفيش رجل في الطريق أو مفيش نافذة محجوزة. `null` هنا يعني
  «مش قادرين نقول» بأمانة — ارسموا حاجة تانية، بلاش تخترعوا رقم.

**لو عايزين ETA حقيقي** فده مزوّد خارجي (Google Routes أو ما شابه) + تكلفة
شهرية + قرار منتج. قولولنا ونرفعه.

### ٤د. الموقع البايت — سايبينه زي ما هو، وده قرار مالك

طلبتوا:

> "If a reading is stale, please send the reading plus an `updated_at` and let
> the client decide, rather than dropping the point."

**مش هنعمل ده، والسبب مش تقني.** القاعدة دي قرار مالك متسجّل من أول يوم وعليه
تست باسمه: `a_reading_that_stopped_arriving_is_removed_not_frozen`. السبب
المكتوب جنبه:

> علامة واقفة على الماب بتتقري «السواق واقف» وبتبعت العميل على التليفون.

القراءة بتتشال بعد **١٢٠ ثانية** = أربع بلاغات ضايعة، يعني موبايل قطع أو قفل أو
بطاريته خلصت. مش تأخير عادي.

وخدوا بالكوا: **`driver.phone` بيفضل موجود في الحالة دي**. سواق موبايله ضرب هو
بالظبط اللي يستاهل اتصال — فالعميل عنده طريق تواصل حتى لما النقطة تختفي.

`updated_at` بيترسل مع كل قراءة **طازة** أصلاً، فلو حبيتوا تحسبوا عمرها عندكم
تقدروا.

**لو مالك المنتج قرر غير كده** نعمله في ساعة: القراءة تترسل مع `is_stale: true`
والكلاينت يرسمها رمادي. بس ده قراره مش قرارنا، ومش هنلغي قاعدة موثّقة من غير
موافقته.

### ٤هـ. `driver.phone` المقنّع (masked / proxy)

طلبتوا واحد من تلاتة، بالترتيب:

1. **رقم حقيقي وقت الرجل الشغّالة** ← ✅ **ده اللي معمول ومنشور من ٣ سبتمبر.**
2. رقم مقنّع ← **مش ممكن دلوقتي**: مفيش مزوّد telephony متركّب في المشروع
   خالص، ولا حتى SMS (الـ OTP نفسه لسه كود ثابت `123456` وبيتكتب في اللوج).
   ده تكامل جديد + تكلفة + قرار منتج.
3. `can_call` + endpoint ← مالوش لازمة طالما (١) شغّال.

الرقم مقفول على **رجل شغّالة** (`Assigned` أو `Started`) من **التلات رجل** اللي
العميل مستنيها، وبيختفي لحظة ما الرجل تخلص. الرجل الرايحة للمغسلة وبس هي اللي
مفيهاش رقم — هدوم العميل رايحة بعيد عنه ومفيش حاجة يتصل عشانها.

**ومفيش شات.** مفيش في المنظومة حاجة بتنقل رسالة بين عميل وسواق، فزرار الشات
يتشال من الديزاين بدل ما يبقى مأشّر على حاجة مش موجودة.

# ٢٠ سبتمبر ٢٠٢٦ — نافذة الاستلام وسعة المغاسل

## الخلاصة: مفيش حاجة كاسرة، وفيه طلب واحد اختياري

كل الـ endpoints زي ما هي، وكل الـ payloads زي ما هي. التطبيق الحالي هيفضل
شغال من غير أي تعديل. اللي تحت ده **إضافة اختيارية** بتفتح سلوك أحسن للعميل.

## اللي اتغيّر في السيرفر

بقى لكل مغسلة **سعة استقبال لكل نافذة** — يعني «مغسلة كذا تستقبل ٥ طلبات بين
٩ و١٢». والسيرفر بقى بيستخدمها لما يختار المغسلة اللي هتاخد الطلب.

**ده مش بيرفض أي طلب.** لو كل مغاسل المنطقة ممتلئة في النافذة اللي العميل
اختارها، الطلب بيتقبل عادي وبيروح لفريق التشغيل يوزّعه بنفسه — نفس اللي بيحصل
دلوقتي لما مفيش مغسلة مغطية المنطقة. مفيش استجابة خطأ جديدة، ومفيش كود جديد
محتاجين تتعاملوا معاه.

كمان المسافات بقت **مسافة طريق حقيقية** بدل الخط المستقيم، فـ `delivery_fee`
في `POST /api/v1/orders/quote` هيطلع **أعلى من قبل** لنفس العنوان — حوالي ٥٠٪
أو أكتر. مفيش تغيير في شكل الرد، بس الرقم نفسه هيختلف، فلو عندكم أي قيم متوقعة
متسجّلة في تستاتكم دي هي السبب.

## الطلب الاختياري: `address_id` في `GET /api/v1/time-slots`

دلوقتي الـ endpoint بياخد `type` و `date` بس:

```
GET /api/v1/time-slots?type=pickup&date=2026-09-22
```

والرد فيه `remaining` و `is_full` محسوبين على مستوى المنصة كلها.

**لو بعتّوا `address_id` كمان:**

```
GET /api/v1/time-slots?type=pickup&date=2026-09-22&address_id=42
```

السيرفر بيعرف ساعتها المنطقة، وبيرجّع حقل جديد **`laundries_full`**: هل كل
المغاسل اللي بتغطي العنوان ده وصلت سعتها في النافذة دي. ولو بعتّوا `service_id`
كمان بيضيّق الحساب على المغاسل اللي بتقدّم الخدمة دي بالذات. وحقل `is_full` الموجود بيضم `laundries_full` جواه **فقط** لو صاحب المنصة اختار
إعداد «إخفاء النافذة» من الداشبورد — فلو انتوا بتعتمدوا على `is_full` زي دلوقتي،
السلوك ده بيشتغل لوحده من غير أي كود جديد عندكم.

`laundries_full` بيرجع `null` لما السؤال مش له إجابة: مفيش عنوان، أو العنوان
من غير منطقة، أو مفيش مغاسل بتغطي المنطقة أصلاً، أو النافذة دي للتسليم بس.
`null` هنا **مش** معناها «مليانة».

الباراميتر **اختياري بالكامل**. من غيره كل حاجة تشتغل زي دلوقتي بالظبط.

**مش محتاجين رد فوري.** قولولنا بس لو ده سهل عندكم في شاشة اختيار الميعاد، ولا
لأ — عشان لو لأ هنسيب الإعداد على وضعه الحالي ومحدش هيحس بفرق.

## ١. `GET /api/v1/driver/tasks/history` — تلات باراميترات جديدة

كانت بتاخد `state` بس. بقت بتاخد:

| البارامتر | القيم | الحالة |
|---|---|---|
| `state` | `all` · `completed` · `failed` · `cancelled` | `cancelled` 🆕 |
| `kind` | `collection` · `delivery` | 🆕 |
| `date` | `YYYY-MM-DD` | 🆕 |
| `query` | نص — رقم الطلب أو اسم العميل | 🆕 |
| `page` · `per_page` | `per_page` من ١ لـ٥٠، افتراضي ٢٠ | كانت شغالة |

`date` هو **يوم المندوب المحلي**، بيتحوّل لمدى UTC على السيرفر قبل الاستعلام —
ابعتوا التاريخ زي ما هو ظاهر في الـdate picker. صيغة غلط بترجّع **422**.

`kind` بيجمّع الأربع رجلين اتنين اتنين:
`collection` = `pickup_from_customer` + `collect_from_laundry` ·
`delivery` = `deliver_to_laundry` + `deliver_to_customer`.

> `GET /driver/tasks` كانت بتاخد `kind` و`query` **من الأول** — التطبيق مش
> بيبعت `kind` وبس.

## ٢. `TaskStatus` — حالة جديدة: `cancelled`

القيم بقت: `pending` · `assigned` · `started` · `completed` · `failed` ·
**`cancelled`**.

**امتى بتظهر:** لما الطلب يروح لـ`cancelled` أو `returned`، كل رجلة **مفتوحة**
بتتقفل على `cancelled`. الرجلين اللي خلصوا فعلًا بيفضلوا `completed`.

**اللي اتغيّر عمليًا للتطبيق:**

- الرجلة الملغية **بتخرج من `GET /driver/tasks`** وبتدخل `history`. قبل كده كانت
  بتفضل في «مهامي» للأبد من غير أي طريقة تقفلها.
- `status_label` بترجع «Cancelled» مترجمة حسب هيدر `lang`.
- المهمة **بتحتفظ بـ`driver_id`**، فبتفضل في سجل المندوب اللي كانت معاه.

⚠️ **لازم تتعاملوا مع القيمة دي في أي `switch`/`match` على `status`** — أي كود
بيفترض خمس قيم بس هيقع عليها.

## ٣. `POST /api/v1/complaints` — `order_id` بقى يقبل طلبات المندوب

كان الفحص على الطلبات اللي الشخص **طلبها كعميل**، فمندوب بيبعت رقم طلب هو وصّله
كان بياخد **404**. بقى المندوب يقدر يسمّي أي طلب كان ليه رجلة فيه.

الرفض لسه موجود لأي طلب ملهوش علاقة بيه — ٤٠٤ زي ما كان.
