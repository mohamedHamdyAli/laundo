## اللي لازم تغيّروه في التطبيق

ده الجزء العملي. الباقي شرح.

### ١. بدّلوا كل قراءة تاريخ على الحقل الـ `_iso`

أي مكان بتقروا فيه `due_at` أو `started_at` أو `completed_at` وبتحاولوا تبارسوه
أو ترتبوا بيه أو تحسبوا منه فرق — بدّلوه بالتوأم بتاعه.

```dart
// قبل — دي جملة، مش تاريخ
final due = task['due_at'];          // "خلال ساعتين" / "in 2 hours"

// بعد
final due = task['due_at_iso'] != null
    ? DateTime.parse(task['due_at_iso'])   // 2026-09-13T18:00:00+03:00
    : null;                                // معناها: مفيش ميعاد متفق عليه
```

`due_at` القديم **سايبينه زي ما هو** لو عايزين تعرضوه كنص جاهز. بس متبارسوهوش.

### ٢. الماب: استعملوا `destination_location` في الليستة

مبقاش لازم تفتحوا تفاصيل التاسك عشان تعرفوا هي رايحة فين.

```dart
final point = task['destination_location'];   // {lat, lng} أو null
if (point != null) {
  marker(point['lat'], point['lng']);
} else {
  showAddressTextOnly(task['destination']);
}
```

**مهم:** `null` معناها محدش حط الدبوس. **متحطوش (0, 0)** — دي نقطة في وسط
المحيط الأطلنطي.

### ٣. الـ pagination: اقروا `meta` مش `msg`

ده على الأرجح اللي كان بيلغبطكم أكتر حاجة. `msg` كانت بترجع صفحة HTML كاملة.

```dart
// كان بيرجع: msg: "<nav class=\"d-flex justify-items-center...\">..."
// بقى:       msg: ""

final meta = body['meta'];
meta['current_page'];   // 1
meta['per_page'];       // 15
meta['has_more'];       // true / false  ← ده اللي يوقف الـ infinite scroll
meta['total'];          // 42
meta['last_page'];      // 3
```

قبل كده `meta` كانت `{}` فاضية **دايمًا**، فلو كنتوا بتتصرفوا حواليها — دلوقتي
فيها اللي محتاجينه.

### ٤. شيلوا أي workaround عملتوه لترتيب التاسكات

الليستة بقت مستقرة. لو كنتوا بترتبوا محليًا بعد ما توصل، الترتيب بتاعنا بقى:
أقرب ميعاد ← اللي من غير ميعاد في الآخر ← رقم الرجل ← الـ id.

### ٥. `steps[].reached` بقت موثوقة

لو كنتوا بتشتغلوا حواليها في شاشة التتبّع، شيلوا الـ workaround. وخدوا بالكم:
ممكن ترجع `reached: true` و `at: null` مع بعض — اقرا [البند ٣](#٣-تاسكات-خلصت-بترجع-بحالة-غير-مكتملة).

## البنود بالتفصيل

### ١. تاريخ ووقت التسليم

#### المشكلة كانت أكبر من اللي اتبلّغ عنه

إنتوا قلتوا «بيرجع null أحيانًا». الحقيقة أوسع: **إنتوا مكنتوش بتاخدوا تاريخ
أصلاً، ولا مرة**. الحقل كان بيترسل كده:

```php
'due_at' => humanDate($task->due_at)
```

و `humanDate()` من غير format بتنادي `diffForHumans()` — يعني اللي كان واصلكم
«منذ ساعتين» / «in 2 hours». نص، مترجم حسب الـ `lang` header، **وبيتغيّر كل ما
تطلبوا الـ endpoint**. مش قابل للبارس ولا للترتيب ولا للمقارنة.

ومكنش في `due_at` بس: **١٦ حقل وقت في ٧ كنترولرز** كانوا كده، وفي نفس الوقت
الـ API كان مستعمل **تلات فورماتات مختلفة** (ISO 8601 في ٥ أماكن، `Y-m-d` في
٨، والنص النسبي في ١٦). عشان كده سؤالكم كان «أكدولنا على الـ format وثباته» —
سؤال في محله تمامًا.

#### الحل

`isoDate()` جديدة في `app/Helpers/Helpers.php`، وكل حقل نسبي بقى له توأم بنفس
الاسم `+ _iso`:

| الـ endpoint | الحقول الجديدة |
|---|---|
| `GET /api/v1/driver/tasks` | `due_at_iso` |
| `GET /api/v1/driver/tasks/{id}` | `due_at_iso` · `started_at_iso` · `completed_at_iso` |
| `GET /api/v1/driver/tasks/history` | `due_at_iso` · `started_at_iso` · `finished_at_iso` |
| `GET /api/v1/driver/summary` | `current_task.due_at_iso` |
| `GET /api/v1/driver/earnings` | `at_iso` |
| `GET /api/v1/orders` · `GET /api/v1/orders/{id}` | `created_at_iso` |
| `GET /api/v1/orders/{id}/track` | `steps[].at_iso` |
| `GET /api/v1/orders/{id}/review` | `confirmed_at_iso` |
| `GET /api/v1/orders/{id}/queries` | `asked_at_iso` · `answered_at_iso` |
| `GET /api/v1/orders/{id}/payments` | `paid_at_iso` |
| `GET /api/v1/orders/{id}/refunds` | `requested_at_iso` · `settled_at_iso` |
| `GET /api/v1/notifications` | `at_iso` |
| `GET /api/v1/wallet/transactions` | `at_iso` |

الشكل: `2026-09-13T18:00:00+03:00` — ISO 8601 **بالـ offset**، فمحدش محتاج
يخمّن الـ timezone بتاعة السيرفر.

#### طلب الـ `required` — مترفض، ودي الأسباب

طلبتوا: «لو فيه تاسك مش متسجل له تاريخ تسليم، لازم يترفض وقت الإنشاء». ده
هيكسر فلو شغّال دلوقتي. `due_at` بيبقى `null` في **حالتين مشروعتين**:

1. **أوردر اتعمل من غير شباك تسليم.** `delivery_date` و `delivery_slot_id`
   الاتنين `nullable` في `app/Http/Requests/Api/V1/OrderRequest.php` وفي الـ
   migration. العميل ممكن يحجز الاستلام بس ويسيب التسليم.

2. **رِجل اتأجّلت.** لما سواق يأجّل رجل، `TaskService::clearSchedule()`
   **بيمسح التاريخ والـ slot عن قصد** وبيبعت للعميل يحجز ميعاد جديد. ده مش
   باج، ده الفلو.

يعني `null` هنا **حالة حقيقية اسمها «لسه مفيش ميعاد متفق عليه»**، مش بيانات
ناقصة. الـ API بقى بيقولها صراحة بدل ما يبعت null صامت.

**اللي محتاجينه من التطبيق:** اعرضوا «لم يُحدَّد بعد» بدل ما تعرضوا فراغ أو
تحاولوا تخمّنوا تاريخ.

> لو الشركة عايزة فعلاً تمنع إنشاء أوردر من غير تاريخ تسليم — ده **قرار منتج**
> مش باج، وممكن ننفّذه بسرعة. بس محتاج قرار من صاحب المنتج الأول، وهيحتاج نقرر
> إيه اللي يحصل للرجل المتأجّلة.

### ٢. الإحداثيات

#### اللي لقيناه

- **تفاصيل التاسك** كان فيها `address.lat` و `address.lng` — بس **للرجل اللي
  عند العميل بس**.
- **ليستة التاسكات** مكنش فيها إحداثيات خالص، `destination` كنص شارع وبس.
- **رجلتين المغسلة** (تسليم للمغسلة، واستلام منها) كانوا بيرجعوا `null`
  **مكتوبة بالإيد في الكود**:

  ```php
  : ['street' => $order?->laundry?->address, 'lat' => null, 'lng' => null],
  ```

  رغم إن `laundries.lat` و `laundries.lng` أعمدة موجودة ومليانة. يعني **نص
  الرحلة مكنش ليه ماب أصلاً**.

  وكمان لو كنا شيلنا الـ null دي لوحدها مكنش هيحصل حاجة: الـ eager load كان
  `laundry:id,name,address,phone` من غير `lat,lng`، والـ constrained eager
  load بيرجع `null` في صمت لأي عمود مش مذكور. الاتنين اتظبطوا.

#### الحل

ميثود واحدة جديدة `TaskType::coordinatesFor()` بتردّ على **الأربع رجل**، جنب
`destinationFor()` اللي بيرد بالشارع — الاتنين بيوصفوا نفس المكان فمينفعش
يكونوا في مكانين.

```jsonc
// GET /api/v1/driver/tasks  →  data[]
{
  "destination": "شارع التحرير، الدقي",
  "destination_location": { "lat": 30.0561, "lng": 31.2003 },   // جديد
  "due_at": "خلال ساعتين",
  "due_at_iso": "2026-09-13T18:00:00+03:00"                     // جديد
}
```

```jsonc
// GET /api/v1/driver/tasks/{id}  →  data.address
// دلوقتي بيرجع lat/lng في الأربع رجل، المغسلة كمان
{ "street": "...", "lat": 30.0444, "lng": 31.2357 }
```

```jsonc
// GET /api/v1/orders/{id}/track  →  data
{
  "driver":            { "location": { "lat": 30.05, "lng": 31.21 } },  // النقطة الحية
  "pickup_location":   { "lat": 30.0561, "lng": 31.2003 },              // جديد
  "delivery_location": { "lat": 30.0561, "lng": 31.2003 }               // جديد
}
```

النقطة الحية بتاعة المندوب كانت بتتحرك على ماب مالهاش أي مرجع — العميل مكنش
يعرف العربية قربت من شارعه ولا لأ.

#### ملحوظة مهمة على الـ endpoint اللي قصدتوه

`GET /api/v1/orders/{id}/track` هو endpoint **العميل**، مقفول على أوردراته هو
(`$request->user()->orders()`). **توكن السواق بياخد منه 404.**

لو تطبيق السواق بينادي عليه فده سوء فهم عندنا أو عندكم — قولولنا وهنظبطه. عشان
كده غطّينا الاحتمالين: الإحداثيات اتضافت في **تاسكات السواق** (ليستة وتفاصيل)
**و** في **الـ track بتاع العميل**.

### ٣. تاسكات خلصت بترجع بحالة غير مكتملة

#### اللي لقيناه

مقدرناش نكرّرها في المسار الطبيعي — جدول الانتقالات في `OrderStatus` خطّي
ومفيش حالة بتتخطّى، ومفيش أي كود بيغيّر حالة الأوردر من غير ما يعدّي على الـ
state machine (اتأكدنا بالبحث). يعني في المسار العادي كل خطوة بيتكتبلها صف.

**بس** `OrderTimeline` كان بيقرّر كل خطوة **من صفها هي بس**:

```php
'reached' => $log !== null,
```

من غير أي ضمان تصاعدي. فصف واحد ناقص لأي سبب — تعديل يدوي على الداتابيز، أو
أوردر قديم اتعمل قبل ما خطوة تتضاف للقائمة — والخطوة دي بتفضل `false`
**للأبد**، حتى والأوردر واصل `delivered`.

ده بالظبط اللي إنتوا شايفينه: الخطوة الأخيرة `true` وواحدة في النص `false`.

#### الحل

```
قبل:  [✓] [✓] [✗] [✓] [✓] [✓] [✓] [✓]    ← بيتقرا إن فيه حاجة اتخطّت
بعد:  [✓] [✓] [✓] [✓] [✓] [✓] [✓] [✓]
```

خطوة ورا خطوة متعدّاة بقت بتتحسب متعدّاة. **بس `at` و `at_iso` بيفضلوا `null`**
في الحالة دي — إحنا عارفين إنها حصلت، مش عارفين **إمتى**، واختراع وقت على شاشة
تتبّع أسوأ من خانة فاضية.

اللي فعلاً محصلش يفضل `false` طبعًا.

**اللي محتاجينه من التطبيق:** لو `reached: true` و `at: null` مع بعض، اعرضوا
الخطوة كمتعدّاة من غير وقت.

### ٤. ترتيب التاسكات

#### اللي لقيناه

الليستة **مكنتش عشوائية**، كانت **غير مستقرة** — وده فرق مهم. الـ query كان:

```sql
ORDER BY due_at IS NULL, due_at
```

يعني: الأقرب ميعاد الأول، واللي من غير ميعاد في الآخر. **بس مفيش فاصل تعادل.**

والتعادل هو الحالة الشائعة هنا لسببين: الأربع رجل بتاعة الأوردر الواحد
بيشاركوا نفس الشباك الزمني، والرجل اللي اتأجّلت مالهاش ميعاد خالص (البند ١).
MySQL مبتوعدش إنها ترجّع الصفوف المتعادلة بنفس الترتيب مرتين، فذيل الليستة كان
بيتخلط بين الطلبات.

**ومع الـ pagination ده أسوأ:** التاسك ممكن يظهر في صفحة ١ وصفحة ٢ مع بعض، أو
ميظهرش في ولا واحدة فيهم.

#### الحل

`OrderTask::scopeInDueOrder()`:

```sql
ORDER BY due_at IS NULL,   -- اللي من غير ميعاد في الآخر
         due_at ASC,       -- الأقرب ميعاد الأول
         sequence ASC,     -- بعدين رقم الرجل (١ استلام … ٤ تسليم)
         id ASC            -- بعدين الأقدم
```

المعيار ده **متأكّد عليه** حسب طلبكم في البند ٤. معناه العملي إن عند التعادل
الكامل، كل رجل الاستلام بتيجي الأول وبعدين رجل التسليم — وده اللي سواق بيخطّط
خط سير بيحتاجه.

والـ history أخد نفس المعاملة على `updated_at`، لأن مجموعة رجل بتخلص في نفس
اللحظة بتشارك نفس الثانية.

### ٥. حاجة مكنتش في ليستتكم — وعلى الأرجح كانت بتوجعكم

كل endpoint بيرجع list في الـ API كان بيحط **صفحة HTML كاملة** في `msg`:

```
msg: "<nav class=\"d-flex justify-items-center justify-content-between\">
        <div class=\"d-flex justify-content-between flex-fill d-sm-none\">
          <ul class=\"pagination\">…"
```

السبب: الهيلبر كان معرّف `successReturnPaginated($paginator, $msg)` وكل مواضع
النداء مكتوبة `($items, $paginator)` — فالـ paginator كان بيقع في خانة الرسالة،
وPHP بتحوّله لنص عن طريق `__toString()` اللي **بيرسم الـ Blade pagination
view**.

ونتيجة تانية: **`meta` كانت `{}` فاضية في كل list في الـ API** — لا `total` ولا
`has_more` ولا `last_page`.

الاتنين اتصلّحوا. الـ endpoints المتأثرة:

`GET /api/v1/orders` · `GET /api/v1/notifications` ·
`GET /api/v1/wallet/transactions` · `GET /api/v1/driver/tasks` ·
`GET /api/v1/driver/tasks/history`

> ملحوظة: الـ HTML كان بيبان **بس لما يكون فيه أكتر من صفحة** — Laravel مبترسمش
> حاجة لو الليستة صفحة واحدة. عشان كده كان بيظهر ويختفي، وصعب تكرّره.

## حاجات محتاجين ردكم عليها

1. **تطبيق السواق بينادي على `GET /api/v1/orders/{id}/track`؟** لو أيوة، ده
   endpoint العميل ومقفول على توكن السواق (بيرجع 404). قولولنا عشان نقرر: نعمل
   نسخة للسواق، ولا التطبيق يستعمل `GET /api/v1/driver/tasks/{id}`؟

2. **عايزين `due_at` القديم (النص النسبي) يفضل؟** لو التطبيق بقى بيعتمد على
   `due_at_iso` بس، ممكن نشيل النص النسبي في v2 ونخفّف الـ payload.

3. **قرار الـ `required` على تاريخ التسليم** — مستنيين رد صاحب المنتج، مش قرار
   تقني.

---

## فيه باج تاني لقيناه ومسيّبينه بقرار

**ليستة تاسكات السواق بتعمل query لكل صف** عشان تحسب `can_start` —
`predecessorComplete()` بيعمل `SELECT EXISTS` لكل تاسك. ٨ تاسكات = ٦ queries
زيادة.

مالوش علاقة بالإحداثيات (دي batched في ٣ queries، وفيه تست بيثبت ده)،
ومسيّبينه لأنه خارج نطاق اللي طلبتوه ولمسه بيمسّ منطق بدء المهام في أماكن
تانية. **لو الليستة بطيئة عندكم قولولنا** — يتصلّح في وقت قصير.

## التحقق

- **٧ تستات جديدة** بتغطي البنود الأربعة.
- **كل فيكس اترجّع وشوفنا التست بيقع** قبل ما نرجّعه — تست عمره مفشل متثبتش إنه
  بيختبر حاجة.
- السويت كاملة: **١١٨٥ تست / ٣٨٢٠ assertion**، PHPStan نضيف.
- التوثيق اتحدّث في الـ Postman collection وفي `docs/api-reference.html` —
  الوصف بتاع كل endpoint فيه الحقول الجديدة وشكلها.
